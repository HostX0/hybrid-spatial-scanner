# B-024/B-025 — scene editing, reversal, and constraints

Scope: portable C++20 scene-command processor behind the B-023 revisioned
command gate. This evidence covers host behavior only. The C facade adapter,
durable checkpoint integration, B-035 source-exclusion consumer, iOS build, and
physical-device behavior remain separate integration gates.

## Implemented contract

- `Processor::process` consumes immutable canonical scene JSON plus the exact
  command UTF-8 bytes. It returns a complete immutable candidate scene only for
  an accepted mutation; rejections and conflicts leave the input scene intact.
- All fifteen command envelopes receive strict variant validation. Implemented
  mutations cover supported/pending corners, split/merge, protrusion/recess,
  fixed detached obstructions, planning-layer obstructions, semantic-only
  classification, exact/soft dimensions, topology protection, position
  lock/unlock, unknown regions, and append-only undo/redo.
- Exact command bytes and SHA-256, exact result bytes, before/after revisions,
  event sequence, reversal lineage, and before/after scene snapshots are exposed
  in `JournalRecord`. The store adapter persists its existing
  `HSSProjectCommandRecord` subset and acknowledges durability only at
  checkpoint.
- Generated node/edge/feature/constraint IDs derive deterministically from the
  command UUID plus a stable role/index. Revisions advance once per accepted
  command, independent of wall-clock time or step batching.
- Exact-model distance and position-lock relations enter a bounded analytic
  equality system. The solver uses a rank-screened dense KKT step, bounded
  updates, merit line search, 256-scalar/40-iteration defaults, feasibility
  checks, and final geometry validation. Soft measurements remain residuals,
  not large-weight substitutes for equalities.
- Undo and redo append new accepted records. They restore the recorded model
  state only when current topology matches the expected lineage; they never
  remove source observations or redirect to a replacement target.
- Dynamic exclusion has a typed `DynamicExclusion` record containing command
  and project IDs, project-space bounds, and the inclusive source sequence
  interval. Until B-035 consumes that record against retained observations, the
  result is `pending_unsupported`/`superseded`, with no false applied scene.

## Integration requirements and limits

- Live core calls the processor from its existing serialized command path,
  atomically installs `candidate_scene_json` only when `scene_changed` is true,
  and continues to own raw captured vertices/indices separately. It must not
  rebuild commanded overlays away; later capture reconciliation uses entity
  lineage or returns stale/conflict.
- Store appends exact command/result bytes with before/after revisions and the
  ordered event context, then reports Saved only after its checkpoint commits.
- B-035 must consume `pending_dynamic_exclusions()` and create a subsequent
  accepted source/control revision after it applies the mask. Reason text is
  presentation data, not a geometry protocol.
- External semantic-origin confidence cannot be represented losslessly in the
  current scene schema, so that classify variant is explicitly rejected rather
  than relabeled. Attached obstruction footprints are retained with a pending
  boundary-topology issue and are not subtracted from area.
- The local dense solver implements distance and coordinate-lock equations. It
  explicitly rejects an active hard orthogonal/parallel relation until its
  analytic Jacobian and regression coverage exist.
- No iOS build, device capture, sensor accuracy, checkpoint interruption, or
  physical metrology result was run or inferred here.
