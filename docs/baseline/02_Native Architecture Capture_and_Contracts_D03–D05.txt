Native Architecture, Capture & Contracts
Hybrid Spatial Scanner | Phase 2 | D03–D05 | Baseline v1.1
v1.1 implementation notice: D14 defines research-backed dependency decisions, D15 extends reconstruction and constraints, and D16 plus the engineering reference pack define the exact ABI, seven schemas, command semantics and ownership. These supersede earlier illustrative interfaces while preserving this document's offline architecture and capture requirements.
D03 — Native App Architecture & Module Boundaries
1. Technology and execution boundary
Use Swift 6 for the native iOS application and C++20 for the portable geometry core. Select iOS 17 as the minimum deployment baseline, with runtime capability checks for scene depth and reconstruction. The exact released Xcode, SDK and compiler patch versions must be recorded and pinned after the first successful build; this document does not claim a tested toolchain.
The C++ engine is compiled into the application. Swift invokes it through a narrow C-compatible facade, not a network API. No server is required for capture, geometry, guidance, save/reopen, review or required exports. Python is reserved for development/benchmark tools. Go is a possible future account/sync service, not an MVP dependency.
Swift supports direct C++ interoperability, but ownership and API compatibility still require care. The facade keeps STL containers, Swift classes, exceptions and allocator ambiguity out of the shared boundary. Metal or local Core ML may be added only for demonstrated needs, not as premature complexity. [SRC-10] [SRC-11] [SRC-12]
2. Module map
ScannerApp owns screens, navigation and app lifecycle. ScanCapture owns the camera/AR session and normalizes public platform events. ScanContracts owns schemas, units and identifiers. SpatialCore owns geometry, topology and constraints. SpatialBridge owns Swift/C lifetimes and error translation. ScanGuidance owns target-specific quality messages. ScanStore owns manifests, chunks, journals and recovery. ScanPlan owns plan projection and annotation layout. ScanScene owns captured/structured 3D viewing. ScanExport owns frozen-snapshot export transactions. ScanReplay feeds recorded normalized events to the core; do not call this module ReplayKit.
Dependencies flow from UI to services/contracts and from the bridge to the core. SpatialCore has no UIKit, ARKit, HTTP or account dependency. Exporters consume accepted snapshots, not mutable live engine internals. The project index is rebuildable from manifests.
3. Session ownership and platform integration
Use one shared ARSession where the tested SDK configuration permits it. RoomPlan receives that session and contributes semantic/parametric proposals; ARKit contributes calibrated depth, poses and mesh events. Apple's custom-session initializer supports supplying an ARSession, but the exact desired combination of frame semantics and reconstruction must be tested on hardware. [SRC-01] [SRC-02]
The Phase 2 spike must record configuration ownership, supported semantics, delegate behavior and actual data availability. Do not run two independent camera sessions and pretend their coordinates match. If coexistence is inadequate, use an explicitly documented ARKit-led fallback with reduced platform semantics. Do not claim access to Apple's private tracking or pose graph.
4. Concurrency and ownership
The main actor handles UI and render state. A capture-normalization queue validates/copies frame data. One serial engine-owner queue applies events and commands. Storage writes and exports run on separate bounded workers. UI updates consume immutable snapshots. No large point-cloud fitting or archive writing occurs synchronously on the main actor.
Replaceable frame events may be dropped under backpressure, with counts recorded. Commands, session transitions and mesh-anchor removals are never silently dropped. Initial targets are adaptive 30–60 fps presentation, up to 10 Hz incremental geometry and up to 5 Hz quality presentation. These are proposed budgets, not measured performance.
Platform buffers are borrowed only within documented lifetimes. Any asynchronous consumer receives an owned copy or a safely retained buffer with explicit release. Snapshot handles remain valid independently of later mutations. Destruction cancels pending work before freeing engine resources.
5. Revision and transaction model
Every accepted SceneSnapshot has a monotonically increasing scene_revision, capture/session provenance and referenced evidence IDs. Live previews may be provisional; export and durable save use accepted snapshots. A pending command preview is not a saved result.
Mesh anchor updates replace the prior contribution for that anchor ID; removals create tombstones. Repeated updates must not duplicate the same wall. Local event logs allow deterministic reconstruction of accepted commands and evidence ordering.
6. Build and dependency policy
Build the portable core with CMake and CTest. Integrate a reviewed static library/package into the iOS target. Pin dependency versions and licences. Add external geometry libraries only after a concrete need, supported iOS build and licence review. Do not adopt a large library merely because it advertises point-cloud processing.
Baseline storage remains local and source-preserving. Backup exclusion is an OS hint rather than an absolute guarantee; privacy wording and user controls are specified in D10. Optional cloud services cannot become a hidden capture dependency.
7. Phase 2 acceptance
On a real supported phone, capture public depth/calibration/mesh data, save it, reopen it offline and replay it through the engine. Apply one reversible live command. Record the actual toolchain and supported session configuration. Simulator UI success is not sensor validation.
D04 — Capture, Coordinate Systems & Deterministic Replay
1. Normalized event stream
Record FramePacket, MeshAnchorEvent, RoomProposalEvent, SessionEvent and UserCommand records. Each includes schema_version, capture_id, session_epoch, event_sequence and monotonic timestamp_s. Wall-clock time is metadata only; do not replace sensor timing with fabricated UTC timestamps.
FramePacket includes image/depth dimensions, pixel formats and strides, calibrated intrinsics, T_world_camera, tracking state, image orientation, depth confidence when supplied and optional retained keyframe references. Record availability explicitly; missing optional data is not zero-filled evidence.
Room proposals retain platform identity, category and geometry with their source version. They are proposals for our structured scene, not the canonical truth. Raw public inputs and accepted derived geometry remain distinguishable.
2. Coordinates and units
All physical geometry uses metres. World/project coordinates are right-handed with +Y up. Matrices are column-major. Use Float64 for canonical geometry and numerical operations; raw depth and rendering buffers may use Float32. A project origin is not geographic north. [SRC-09] [SRC-13]
Every accepted session epoch has a T_project_world transform. A reset creates a new epoch. Cross-epoch merging requires a validated relationship; otherwise preserve separate capture regions and ask for relocalization or reference alignment.
FloorFrame contains origin O and orthonormal U, V, N with U cross V = N. Default U=(1,0,0), V=(0,0,-1), N=(0,1,0). A project point projects to plan coordinates dot(P-O,U), dot(P-O,V). The exporter performs any screen y inversion once, explicitly.
3. Calibrated depth unprojection
Use the depth camera's properly scaled/aligned intrinsics. For a calibrated optical convention with x right, y down and positive forward z: x=(u-cx)*z/fx and y=(v-cy)*z/fy. Convert to the AR camera convention as p_ar=(x,-y,-z), then apply T_world_camera and the accepted project transform. This is a convention contract that must be checked against actual buffers and orientation tests.
Never use the UIKit display transform as a substitute for depth/RGB calibration. Test crop, rotation, resolution scaling, portrait and landscape explicitly. Reject nonfinite, nonpositive and otherwise invalid depth samples. Depth is measured in metres; confidence is an ordinal platform value, not a calibrated probability. Use 255 for unavailable confidence in the normalized contract. [SRC-04] [SRC-05]
4. Mesh updates
Store anchor-local geometry with anchor ID, revision and transform. Convert through the current accepted anchor transform when deriving project geometry. Replace an anchor contribution on update and remove it on tombstone. Preserve source references for fitted surfaces and features.
Plane detection can affect the reconstructed mesh representation. Retain depth evidence separately and test the chosen configuration rather than assuming the mesh contains every original detail. [SRC-03]
5. Recording and workload
Initial keyframe triggers are 0.15 m translation or 10 degrees rotation, conditioned on image quality and useful coverage. They are tuning hypotheses, not sensor limits. Geometry processing is sampled at up to 10 Hz with explicit dropped-frame counters. Commands and structural events remain ordered and lossless.
Use chunked storage with a 16 MiB target chunk and a 256 MiB maximum individual chunk. Bounds are defensive defaults, not a maximum physical room size. Stream long captures; do not keep all images in memory. Record thermal/storage pauses and the reason for every discontinuity.
6. Tracking and multizone capture
Low light and weak texture can impair camera-based tracking even with LiDAR. A dim room may still produce depth while pose quality is insufficient. Ask for lighting or a useful viewpoint and stop committing precise geometry when tracking is invalid. [SRC-13]
Connected rooms first use a continuous shared coordinate frame. Large halls may be divided into zones with overlap and explicit seam checks. Independent zones are not automatically aligned by matching room names. Separate floors, elevators and full-building mapping are deferred until their coordinate policies are implemented.
7. Replay contract
Replay feeds recorded normalized events to our engine in deterministic order. It does not rerun Apple's private tracker from raw camera footage. Record platform room proposals when their contribution must be reproduced. Fix random seeds and deterministic iteration ordering where possible; compare CPU results within declared numerical tolerances.
The same input stream, command journal, engine version and tuning profile must reproduce the same topology and bounded geometry. A simple exact synthetic fixture uses an initial 1e-6 m numerical tolerance; this is floating-point test precision, not physical sensor accuracy.
8. Required capture tests
Test known transforms, projection round trips, depth/RGB orientation, intrinsics scaling, anchor replacement/removal, invalid depth, tracking loss, epoch reset, full queue behavior, checkpoint interruption and replay ordering. Store at least one consented physical difficult-room capture before advanced algorithm work is considered validated.
D05 — Swift–C++ Interfaces, Data Model & Project Format
1. Schema conventions
JSON schema baseline is 1.1 and ABI major version is 1. Sequence/revision counters use uint64 in memory and canonical decimal strings in JSON. Reject unknown required units, incompatible major versions and unsupported critical enum values. UUIDs identify production entities; readable fixture IDs are allowed only in tests. Counts and byte lengths use explicitly sized integer types with overflow checks.
Geometry origin is observed, fitted, user_measured, inferred or unknown. Semantic origin is platform, local_model, user, imported or unknown. Quality state is provisional, needs_review, ready or invalid. Null uncertainty means unknown; zero means an actual zero only when justified. User semantic confirmation does not improve metric accuracy.
2. Core entities
Project contains identity, units, basis, capture list and committed scene pointer. Capture contains session epochs and source event references. SurfacePatch contains geometry, support IDs and fit diagnostics. BoundaryNode/BoundaryEdge contain topology and endpoint relationships. Feature contains protrusion/recess/obstruction topology and protection state. RoomRegion contains outer loop, holes and area policy. ObjectInstance contains labels and geometry references. Constraint contains type, targets, source and status. QualityIssue contains target, evidence and action. SceneSnapshot freezes a revision. ExportRecord binds formats and hashes to that revision.
3. C-compatible interface
The normative v1.1 declarations are delivered in include/hss/hss_api.h, with ownership and integration rules in D16. Use that complete tested header rather than an abbreviated prose signature. Host C/C++ compilation and Swift import have been checked; the scanner function implementations and iOS linkage remain production work.
Extensible ABI messages begin with abi_version and struct_size; fixed identity/math POD values do not. Submission validates and copies required data synchronously, without retaining borrowed Swift pointers. The wrapper serializes engine calls. Each acquired immutable snapshot has one owning handle and exactly one release; pointer copies are borrows. Snapshots outlive the engine. No C++ exception crosses the facade.
Copy-out functions return the required count when capacity is insufficient and never write past the buffer. Outputs initialize to null/zero on failure. Partial output cannot masquerade as a complete snapshot.
4. Error contract
HSS_OK=0. Nonzero results include invalid_argument, unsupported_version, unsupported_capability, invalid_calibration, invalid_coordinate_frame, stale_revision, constraint_conflict, insufficient_evidence, buffer_too_small, resource_limit, canceled, internal_error, NOT_READY and DUPLICATE_MISMATCH. Catch exceptions at every public entry point and return an error with a diagnostic ID that contains no images or private room content.
5. Command envelope
A command contains command_id, schema_version, project_id, expected_scene_revision, event_sequence, type, targets, payload and user_intent. A result is applied, rejected, conflict or superseded. Commands are small JSON records; bulk geometry uses binary buffers.
Example: protect_feature targets feature-rib-01, preserve_topology=true, lock_position=false and user_intent='Keep this wall protrusion during refinement'. Production IDs are UUIDs. Protection preserves feature structure while permitting coordinate refinement. Locking coordinates is a different command.
Supported commands are mark_corner, split_edge, merge_edges, mark_protrusion, mark_recess, mark_obstruction, classify_object, set_dimension, protect_feature, lock_position, unlock_position, mark_unknown, exclude_dynamic_region, undo and redo. Preconditions and conflict behavior are specified in D07 and the S03 command catalog.
set_dimension requires value, units, endpoint references and measurement source. A guessed typed value is inferred. Contradictory hard constraints return a visible conflict and preserve the prior valid snapshot. Never silently rescale the entire room to satisfy one number.
6. Project package
The canonical .hsscan project is a directory; a ZIP is the portable share wrapper. Required structure: manifest.json; capture/<id>/metadata.json; capture/<id>/chunks/<chunk>.bin; capture/<id>/events.ndjson; images/<id>.heic; mesh/<anchor>/<revision>.bin; commands/journal.ndjson; scenes/<revision>/scene.json and geometry.bin; quality/<revision>.json; exports/index.json; previews/plan.png.
Binary records are little-endian with magic, version, type, count, stride, payload length and checksum reference. Canonical geometry uses doubles. JSON carries metadata and references, not millions of serialized point coordinates.
7. Atomic save and migration
Write new chunks and derived assets to temporary paths, validate lengths/checksums, commit the snapshot and update the manifest last. Preserve an older valid manifest until replacement succeeds. Recovery selects the latest internally valid commit, not merely the newest timestamp.
Migrations are copy-on-write and preserve the original until validation passes. A newer unsupported critical schema is rejected with an explanation; never load it with guessed units. The project index is a cache, not the only source of truth.
8. Defensive import limits
Initial defensive limits: 8 GiB expanded project, 20,000 files, 256 MiB individual binary chunk and 16 MiB JSON record. Stream validation and enforce count/stride/byte consistency before allocation. Reject path traversal, absolute archive paths, zip bombs, nonfinite coordinates and references to missing entities. These are configurable safety bounds, not performance claims.
9. Contract acceptance
Compile the C header from C and C++. Test layout/version checks, ownership lifecycle, repeated snapshot release rules, small copy-out buffers, exception translation, stale revisions, malformed commands, archive traversal and allocation overflow. Run sanitizers where available. Record unexecuted hardware tests explicitly. S03 is the field/command/error catalog; it does not replace these ownership and semantic rules.
