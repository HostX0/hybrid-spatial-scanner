## Delivered contract

`InterruptionRecoveryCoordinator` is an additive portable C++ facade over the
B-007 `DurableSourceStore`. It does not change the durable-store, normalized
replay, ingress, engine, Swift session, C ABI, schema, or Xcode project
contracts. The facade asks the store for its fully hash/length/order-validated
active or previous manifest, applies independent record/count/byte limits, and
checks epoch compatibility before publishing one immutable metadata snapshot.
There is no callback or state-publication point before those checks complete.

Recovery has explicit outcomes for the valid latest revision, a valid latest
revision with retained interruption markers, a validated previous revision
after an invalid or missing newest candidate, no valid durable state,
relocalization-required epoch mismatch, resource/configuration/storage failure,
and publisher rejection. A missing checkpoint is distinct from present but
invalid candidates.

The coordinator observes store-owned files only. Pending files remain visible
as interruption evidence and corrupt active manifests remain untouched after a
fallback. Recovery performs no garbage collection, deletion, repair, manifest
replacement, geometry synthesis, or source-epoch rewrite.

Every recovered non-current source epoch is blocked unless the caller supplies
a nonzero, explicitly accepted B-012 relationship version for that exact epoch
pair. The relationship token authorizes publication only: this module neither
estimates nor applies a transform and exposes the original source epochs
unchanged. Missing authorization returns the blocked epoch set and invokes no
publisher.

The default recovery envelope is 384 retained records, 256 MiB total payload,
256 MiB per record, 20,000 interruption markers, and 384 accepted relationship
tokens. These checks are in addition to B-007 retention limits and fail closed
without publishing state.

## Portable verification

The focused test covers:

- valid latest-state publication exactly once;
- an incomplete pending manifest with the last commit preserved and the
  pending bytes left on disk;
- a truncated/corrupt newest active manifest falling back to the validated
  previous revision without rewriting the corrupt evidence;
- absent and all-corrupt no-valid-state failures with zero callbacks;
- epoch mismatch blocking publication until an explicit accepted relationship
  is supplied, without changing the retained source epoch;
- out-of-order and duplicate candidate event sequences preserving the previous
  committed state;
- independent recovery resource-limit failure before publication; and
- explicit downstream publication rejection after validation.

## Interface and evidence limits

The change adds only a C++ header/source module, its focused host test, evidence,
and CMake test registration. It introduces no C ABI or schema change and no
project-file registration. The production application still needs a platform
adapter that supplies B-012 accepted relationship versions and consumes the
validated state.

No physical iPhone test was run. Host/POSIX results do not verify protected-data
availability, background/foreground transitions, phone lock, process kill at
filesystem boundaries, APFS durability details, low storage, permission
changes, migration, real ARKit relocalization, stale-overlay suppression, or
physical geometry/metrology. Those device cases remain visibly open and must
retain source/candidate evidence on failure.
